# 公众参与试运行方案（提案，尚未执行）

## 判断

无法确保公众一定参与。GitHub 公开只是让人有权限贡献；人们还需要看见项目、相信它、知道自己能做什么，并收到回应。SEO 更偏向带来读者，贡献者通常还需要具体邀请和清楚任务。

我的建议：先做 30 天小规模共建试运行，找到 3–5 位愿意反复参与的人，再扩大推广。该人数是试运行目标，不是预测。执行方法信心中等，实际转化需要数据。

## 贡献路径

| 环节 | 具体做法 | 观察指标 |
| --- | --- | --- |
| 看到项目 | 由发起人在自己已有联系的马来西亚社群分享一条真正有用的内容，再说明需要谁补充什么 | 可获得时看访问量；否则先记录每次分享的渠道与日期 |
| 产生信任 | 公开出处、核对日期、待复核状态；展示真实更正记录 | 完成独立复核的条目数 |
| 愿意开始 | 一次任务只核对一项事实或一个入口；无需编程，可用中文/BM/English 提交 Issue | 首次投稿人数与完整来源比例 |
| 获得回应 | 发起人安排固定维护时间，目标 48 小时内首次回应；无法验证时说明缺少什么 | 首次回应时间中位数、未处理提案数 |
| 再次回来 | 经同意后公开署名致谢，告知贡献实际怎样被采用；邀请参与下一条相近任务 | 第二次贡献人数、重复贡献率 |

## 30 天执行步骤

第 1 周：由发起人邀请约 10 位已有联系的人做小测试。分别请他们找一条资料、报告一个错误或完成一次独立复核。邀请数量是计划，不是实际已邀请人数。未经用户授权，不自动给任何人发消息。

第 2 周：挑选 3 个能在约 15–30 分钟开始的入门任务。示例：核对 My50 当前官方产品页与现有条目是否一致；检查一个 MySejahtera 预约帮助入口；找一份 Sabah 或 Sarawak 的官方交通资料。不得先编造当地规则再请别人证明。

第 3 周：把一个已经完成的更正案例写成简短帖子：原来哪里不清楚、用了什么来源、改成什么。由发起人选择适当的社群分享，遵守群规；不群发、不伪装用户推荐、不购买 star。

第 4 周：查看参与漏斗。有人看、无人投：检查是否任务太大或必须登录 GitHub；有投稿、难合并：检查来源说明与模板负担；合并后没人回来：检查回应速度与实际使用反馈。再决定是否扩大内容范围。

## 可以由你直接发布的邀请文案（草稿）

“我在共建一份《马来西亚好好生活指南》🇲🇾，希望把 My50、EPF、看诊入口与日常生活资料整理得更清楚，每条内容都能查到来源。

不需要会写代码，也不需要一次写一整篇。你可以帮忙核对一条资料、补充你州属的官方入口，或指出一个错误。中文、Bahasa Melayu、English 都欢迎。

你只需要提供：一条想补充的信息＋直接来源链接＋适用地区/日期。我们核验后合并并注明贡献。

阅读：https://choonseng4896-rgb.github.io/how-to-live-better-malaysia/
投稿：https://github.com/choonseng4896-rgb/how-to-live-better-malaysia/issues/new/choose”

## 尚待审批或设置的工作

- 建立并标注 `good first issue`、`help wanted`、`needs-source`、`needs-review` 入门任务；本次未声称这些标签或任务已经配置。
- 可提议“贡献者名单”，先征得贡献者同意，再公开其姓名或账号。
- Search Console 所有权验证与 sitemap 提交需单独完成；本次未执行。
- 若 GitHub 登录成为主要障碍，再评估简单投稿表单；需明确隐私与审核安排，不先做庞大社区系统。
- 初期用 GitHub Issue/PR 记录投稿、来源和合并情况。暂无真实访问统计，不能拿 star 数代替活跃贡献者。

## 推荐观察，而非保证达到的目标

30 天试运行可暂定：10 次明确的小范围邀请、5 份有来源的投稿、3 位首次贡献者、至少 1 位再次贡献者。所有数字均为管理目标，当前基线尚未采集；不是预测或实际成绩。

参考：[Open Source Guides — Building Welcoming Communities](https://opensource.guide/building-community/)。具体邀请规模、48 小时回应和 30 天目标是本项目建议，不是来源中的实证结论。
